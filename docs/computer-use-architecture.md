# Computer Use Architecture Audit

This record captures the repository audit performed before adding macOS Computer Use.
The audited baseline is `chen362/DesktopCommanderMCP` `main` at commit
`e7dd3ab91237a4a4e2c00ad475e85c5f9f163ce9`.

## A. Current MCP architecture

Desktop Commander is a Node.js/TypeScript MCP server built on
`@modelcontextprotocol/sdk` `^1.9.0`. `src/index.ts` creates a custom
`FilteredStdioServerTransport`, loads configuration and feature flags, then connects the
singleton `Server` exported by `src/server.ts`. The server exposes tools, resources and
prompts. Tool definitions and dispatch currently live in `src/server.ts`; Zod schemas live
in `src/tools/schemas.ts`; domain handlers live under `src/handlers/` and `src/tools/`.

The repository also contains a Remote Device CLI. It is not an HTTP, SSE or Streamable
HTTP MCP server. The local MCP hop remains stdio. The externally hosted Remote MCP service
and its HTTP/OAuth endpoint are outside this repository.

## B. Remote MCP data flow

1. `desktop-commander remote` starts `src/remote-device/device.ts`.
2. The device authenticates against the hosted Remote MCP service and connects to its
   Supabase-backed realtime/database channel.
3. `DesktopCommanderIntegration` starts the local Desktop Commander MCP server and connects
   to it with `StdioClientTransport`.
4. The device registers the exact tool list returned by the local MCP server.
5. A remote call arrives over the realtime/database transport, is claimed exactly once,
   and is forwarded unchanged through `Client.callTool()` with `_meta.remote=true`.
6. The complete MCP tool result is stored as JSON and the remote service is notified after
   the result write completes.

Because the bridge forwards the complete MCP result object and stores JSON rather than
flattening content to text, MCP image content blocks can pass through this path. Large image
payload limits still depend on the separately deployed Remote MCP service and must be
verified in that environment.

## C. Tool registration location

`src/server.ts` handles `tools/list` at the `ListToolsRequestSchema` handler. It builds one
large `allTools` array, filters it with `shouldIncludeTool`, and returns it. Computer Use
definitions will be generated by `src/computer-use/tools.ts` and spread into that array only
when the feature is enabled and the platform is supported.

## D. Tool handler location

`src/server.ts` handles `tools/call` and dispatches existing tools through a switch to
functions exported from `src/handlers/index.ts`. The outer handler already performs
telemetry, usage accounting, error conversion, unsupported-parameter warnings and tool
history recording. Computer Use will use one module dispatcher in
`src/computer-use/handler.ts` so individual GUI actions do not enlarge the switch.

## E. Computer Use insertion point

The least disruptive insertion is:

- schemas and tool descriptions in `src/computer-use/`;
- a platform-neutral service and policy layer in `src/computer-use/`;
- a persistent macOS native helper managed by `src/computer-use/macos/`;
- one tool-definition spread in `tools/list`;
- one dispatcher branch in `tools/call`;
- schema-map integration in `src/tools/schemas.ts`;
- configuration defaults in `src/config-manager.ts`.

This keeps terminal, filesystem, process, search, PDF, document, UI and Remote Device code
paths intact.

## F. Existing image content support

Yes. `src/handlers/filesystem-handlers.ts` already returns official MCP image blocks with
`type: "image"`, base64 `data`, and `mimeType` for image files and PDF-extracted images.
`src/types.ts` also models these fields. Computer screenshots can therefore use the same
result shape without inventing another wire format.

## G. MCP transports in this repository

- Local MCP server: custom-filtered stdio server transport.
- Local Remote Device to Desktop Commander hop: MCP stdio client transport.
- Remote Device to hosted service: Supabase realtime broadcast/presence plus a database-row
  fallback/doorbell flow.
- HTTP OAuth/device authorization and the user-facing Remote MCP endpoint: hosted service,
  outside this repository.
- No in-repository SSE or Streamable HTTP server transport was found.

## H. macOS-specific code placement

Platform-neutral contracts, validation, policy and handlers belong in `src/computer-use/`.
macOS process management belongs in `src/computer-use/macos/`; the native Swift helper
source belongs in `src/computer-use/macos/native/`. The helper will be copied into `dist`
during build, compiled for the host on first use, kept alive over a JSON-lines IPC channel,
and restarted on a later call after a crash. Windows and Linux builds must never import or
compile Apple frameworks.

## Additional audit findings

- Computer Use must be opt-in. Existing installs currently have broad filesystem access by
  default, so silently adding GUI control would materially expand authority.
- Existing tool-call logs and history record raw arguments. Computer Use must redact typed
  text before those shared logging paths receive it.
- Remote Device debug logs currently stringify arguments and complete results. They must be
  summarized for Computer Use so typed text and screenshot base64 are not written to logs.
- The existing history layer caps oversized results, which prevents screenshot base64 from
  growing the persistent history indefinitely.
- The project has no Electron runtime. It is a CLI MCP server with embedded MCP App UI
  resources and a separate Remote Device CLI.
- Docker must not advertise Computer Use because a container cannot access the host Window
  Server, Accessibility session or display devices.
- The local audit environment is Linux and has no macOS Window Server. Native GUI behavior
  can be covered by mocks and a macOS-gated integration harness here, but real screen,
  pointer, keyboard and permission tests require an interactive macOS host.
